# Agent 工作规范

本文件适用于所在目录及其子目录；需要约束整个仓库时，应放在仓库根目录。以下文档路径均相对于项目根目录。

## 规则优先级

- 遵循系统、开发者和用户指令；本文件不得覆盖更高优先级的指令。
- 用户在本次会话中已明确给出的授权和约束持续有效，无须重复确认。
- “必须”表示 MUST，“应该”表示 SHOULD，“可以”表示 MAY。
- 推断出的用户意图是工作假设，不能替代用户授权。

## 项目配置

- 交接文档：`docs/HANDOFF.md`
- 项目说明文档：`README.md`
- 设计文档目录：`docs/design/`
- 侦察文档目录：`docs/research/`
- 计划和结果目录：`docs/plans/`
- 计划索引：`docs/plans/INDEX.md`
- Review 文档目录：`docs/reviews/`
- 逆向功能规格说明书目录：`docs/reverse-spec/`
- 文档目录和 `AGENTS.md` 纳入版本管理；是否执行提交、推送遵循下文授权规则。
- Git commit 消息、文档和注释使用中文；代码标识符、命令和专有名词保留原文。
- 文档时间使用 Asia/Shanghai 时区，精确到分钟。

目录和文档按需创建，不预先生成空文件。

## 基本工作原则

- 先理解问题、代码和约束，再提出方案或修改代码；区分已确认的事实和待验证的假设。
- **回答或解决问题前，先搜集足够信息，不可想当然的假设。**
- 独立判断用户方案的合理性；发现错误时，直接说明依据和影响。
- 用户询问某个方案是否合理时，先回答问题，不自动实施该方案。
- 对设计选择给出理由；证据表明判断有误时，及时修正。
- 在已授权范围内持续推进；关键信息缺失且会影响范围或结果时，提出具体问题。
- 用户未指定下一步时，可以结合项目目标提出优先级建议，不自行开始新的开发任务。
- 不主动重构无关代码，不覆盖或回滚用户已有改动。
- 文档引用使用相对于项目根目录的路径，必要时附行号和版本依据，便于复核。
- 流程投入与任务风险相称，不为了满足流程生成没有实质内容的文档。

## 开始任务前

按需检查 `git status`、目录结构、项目说明文档、交接文档、相关设计和计划，以及代码与提交历史。文档可能过时，应结合当前代码和 Git 记录核实。

修改前明确任务范围、涉及文件、相关已有改动和验证方式。简单任务只读取相关上下文，无须遍历整个仓库。

## 文档命名和来源

- `<topic>`、`<tag>` 使用简短、可辨识的名称，单词间用 `-` 分隔。
- `<model>` 使用环境明确提供的实际模型 ID，统一小写，文件名不安全字符替换为 `-`；不得猜测模型名称或版本。
- 无法确定模型 ID 时使用 `model-unknown`，正文说明已知模型信息和未知项。
- PLAN 和 REVIEW 文件名必须包含创建文档的模型标识；后续换模型更新同一文件时保留原文件名，在正文记录更新者和时间。
- `<revision>` 使用所分析提交的前 8 位哈希；分析范围包含未提交或未跟踪内容，或仓库尚无提交时，使用 `WORKTREE`。
- 文档开头记录创建时间、实际模型信息和分析范围；涉及代码结论时记录完整提交哈希。使用 `WORKTREE` 时，记录基准提交（如有）以及相关未提交或未跟踪文件，说明内容尚未固定为提交。
- 新建文件遇到同名时追加数字后缀，不覆盖已有文档；更新现有文档时保留原有引用关系。

## 计划和结果

多步骤、跨模块、改变用户可见行为，或涉及 API、数据结构、配置和数据库的实质修改，必须先建立计划。只读问答、Review、简单单文件局部修改和纯格式修正通常不需要计划；用户明确要求时按其要求执行。

计划命名：`<计划和结果目录>/PLAN-YYYYMMDD-NNN-<model>-<topic>.md`。`NNN` 为当天三位递增编号，创建前检查现有文件，避免冲突。

示例：`PLAN-20260915-001-gpt-6-astra-auth-flow.md`。

计划必须包含：

- 目标、范围和不在本次处理的事项
- 当前状态、依据和约束
- 实施步骤
- 验证方式和完成标准
- 主要风险及必要的回滚方式

实施前至少自查一次，检查设计缺陷、逻辑冲突和遗漏。范围或步骤发生实质变化时，先更新计划再实施。

使用了计划的任务，实施完成后必须在计划和结果目录生成对应结果文件，在计划文件的 `.md` 前追加 `-OUTCOME`，例如 `PLAN-20260915-001-gpt-6-astra-auth-flow-OUTCOME.md`。结果文件沿用计划文件名中的模型标识，正文记录实际执行模型、完成情况、计划偏差、验证结果和遗留问题。

在计划索引中按实际更新时间追加计划与结果文件的相对链接、状态和简要结果。索引不存在时按需创建；历史信息不完整时如实说明，不推测补写。

## 设计

所有设计文档按主题平铺在设计文档目录，命名为 `<topic>-YYYYMMDD-<tag>.md`，例如 `auth-20260915-overview.md`。

涉及库、SDK、模块或对外 API 的重要设计时，明确使用场景、边界和兼容性要求，比较可行方案并说明取舍，定稿前至少复核一次。环境提供 `api-design-zh` skill 时使用；不可用时按上述要求完成设计并说明限制。

UI 设计也是设计文档的一部分，直接放在设计文档目录，简要说明页面、状态和交互范围。具体设计方法、视觉规范和验收要求遵循用户指定的 UI skill，默认参考 ui-design-zh 这个skill；未指定时沿用项目现有约定。

## 实施和验证

- 按已确定的范围和计划实施，优先复用项目现有模式和工具。
- 保留已有改动，提交时仅暂存本次任务的改动；同一文件包含用户改动时应区分处理。
- 不使用未经授权的破坏性操作，包括强制覆盖、批量删除和回滚用户改动。
- 完成修改后进行代码自查，修复本次引入的问题。
- 根据行为变化和风险，运行相关测试、构建、lint 或静态检查；涉及共享行为时扩大验证范围。
- 新增测试应覆盖实际风险和行为，不为简单文档、格式修改或重复实现逻辑而机械增加测试。
- 必要验证失败时先修复；无法完成验证时记录原因、影响和剩余风险，不将其报告为通过。

## Git 提交和推送

- `commit` 和 `push` 是独立动作，分别以用户明确授权为准；授权可来自当前请求或本次会话此前的明确约定。
- 修改文件本身不意味着获得提交或推送授权；已获授权的动作无须重复询问。
- 提交前检查当前分支、暂存区和验证结果，只包含本次授权范围内的改动。
- 必要验证失败或无法执行时，先报告具体情况；只有用户明确接受该状态后，才继续提交或推送。
- 提交消息说明变更和原因；使用了计划时必须包含计划及结果文件的相对路径，新增设计文档时注明其路径。
- 推送前检查远端、目标分支和待推送提交范围；发现范围外提交时先说明情况。
- 不自动使用强制推送；确有需要时必须获得用户对具体目标和操作的明确授权。
- 执行后报告 commit ID 和推送状态，不将本地提交描述为已推送。

## 侦察文档

侦察文档用于记录代码研究结果，说明研究问题、已确认的事实、文件路径和行号依据，以及尚未确认的问题。

命名：`<侦察文档目录>/YYYYMMDD-HHmm-RESEARCH-<revision>-<topic>.md`。来源信息遵循“文档命名和来源”规则。

## Review

- 用户要求 Review 时，默认在回复中给出结果；只有明确要求形成文档时才写入文件。
- 优先关注缺陷、行为回归、规则冲突和缺失的验证，按严重性排序。
- 每条发现说明触发条件、影响和代码或文档依据，给出必要的修正建议；不把个人风格偏好当作缺陷。
- 没有发现问题时明确说明，同时指出相关验证空白或剩余不确定性。
- Review 请求本身不授权修改被审查内容；用户同时要求修复时再实施。

Review 文档命名：`<Review 文档目录>/YYYYMMDD-HHmm-REVIEW-<model>-<revision>-<topic>.md`。

示例：`20260915-1200-REVIEW-gpt-6-astra-WORKTREE-auth-flow.md`。

用户要求复核已有 Review 时，逐条核实并说明依据；需要输出文档时，在原文件的 `.md` 前追加 `-review-verification-<model>`，保留原目录，正文记录本次复核的实际版本。此处 `<model>` 为复核模型，例如 `20260915-1200-REVIEW-gpt-6-astra-WORKTREE-auth-flow-review-verification-gpt-5.6-terra.md`。

## 逆向功能规格说明书（RFS）

用户要求生成 RFS 时，默认覆盖整个仓库；指定模块时只覆盖指定范围。RFS 基于代码恢复现有行为，区分代码事实和未知项，不把改进建议写成现有功能。

内容应覆盖用户可见行为、输入输出、数据边界、状态变化、异常处理、权限配置和外部交互，并提供对应代码依据。

命名：`<逆向功能规格说明书目录>/YYYYMMDD-HHmm-RFS-<revision>-<topic>.md`。

完成后至少复核一次，以不了解原代码的团队能够据此实现行为一致的替代品为目标；对无法从代码确认的外部依赖和运行时行为，明确记录待验证项。

## 交接文档

用户明确要求，或未完成的长任务需要暂停、资源限制影响继续执行时，更新交接文档。不得猜测无法获取的剩余额度。

交接内容包括项目背景、已完成工作、工作区状态、已知问题、待办和建议的下一步，以及相关文档、代码路径和 commit ID。区分已验证结论与假设，让接手者能够继续工作。

## 任务结束时

简要说明完成内容、关键文件、验证结果和未完成事项；执行了提交或推送时报告实际状态。问题解决后结束，不追加无关任务，也不重复索要已经获得的授权。
