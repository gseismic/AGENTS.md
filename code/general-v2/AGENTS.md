# Agent 工作规范

本文件适用于所在目录及其子目录；需要约束整个仓库时，应放在仓库根目录。以下文档路径均相对于项目根目录。

本文件保存通用工作规则、项目特定规则和固定文档入口。项目当前设计、开发文档清单、常驻必读清单和任务进度在对应开发文档中维护，不随日常开发写入本文件。

## 项目特定规则

本区域用于填写用户为当前项目明确指定的规则，例如技术约束、工作方式和交付要求。未指定时保留为空，不自行编造项目要求。

## 规则优先级

- 遵循系统、开发者和用户指令；本文件不得覆盖更高优先级的指令。
- 用户在本次会话中已明确给出的授权和约束持续有效，无须重复确认。
- **在不违反上述指令的前提下，项目特定规则优先于本文件的通用规则。** 未覆盖的事项遵循通用规则。
- “必须”表示 MUST，“应该”表示 SHOULD，“可以”表示 MAY。
- 对用户意图的推断是工作假设，不能作为扩大任务范围或违反用户约束的依据。

## 项目目标（GOAL.md）

`GOAL.md` 表达用户希望项目实现什么，以及大致的功能范围；`AGENTS.md` 约束 Agent 如何工作。目标与规范共同定义项目工作的方向和边界，分析、设计和实施应以此为依据，并遵循上文规则优先级。

- 内容可以只有一句话，也可以是一句话加粗略功能列表；保持简洁，不混入实施步骤、任务进度或待办清单。
- **只有用户明确要求创建或修改项目目标文件时，才允许按指定范围操作 `GOAL.md`。** 未获此类要求，不得创建、修改、追加、重命名或删除该文件；一般开发、文档整理、目标相关功能的实现都不构成修改授权。
- 代码现状、新需求、计划、TODO 或任务完成状态的变化均不触发自动更新。Agent 可以在回复中提出目标调整建议，不能自行写入文件。
- 用户当前明确指令优先于文件中的旧目标；执行新指令不意味着同时获得更新 `GOAL.md` 的授权。不能用代码现状自行替换或缩减用户目标。

## 开发文档总入口（docs/README.md）

根目录 `README.md` 面向项目使用者，说明项目用途、安装、配置和使用方式；`docs/README.md` 面向开发者和 Agent，作为开发文档首页，维护开发说明、阅读顺序、常驻必读清单和分类导航。

- **常驻必读清单在 `docs/README.md` 中维护。** 清单标明文档路径、用途和当前有效状态，收录重要的总体设计、架构边界和长期约束；具体名单及设计正文不复制到 `AGENTS.md`。
- 总入口链接总体设计和各类文档入口；已有专题索引时链接索引，详细条目由对应索引维护，处理日志和任务进度保留在原文档中，避免重复维护。
- 首次形成开发文档时建立总入口；维护已有开发文档而总入口缺失时，依据实际内容补建。新增、移动、重命名或废弃文档导致导航变化时，同步更新相关入口和索引。
- 只登记实际存在的文档，不预先创建空文档或指向不存在文件的链接。文档缺失时如实说明；Markdown 链接相对于入口文件所在目录解析，保证可打开。
- 常驻必读文档保持当前有效内容；被替代或废弃时更新清单及替代关系，历史方案通过相关文档保留追溯入口。

## 基本工作原则

- **每次收到用户输入后，必须在随后首次回复中，先用清晰、简洁的语言主动复述所理解的用户意图，再回答或继续执行。** 概括用户希望达成的目标、本次要求和关键约束；多项要求逐项概括，追加或更正要求时说明对当前任务的影响，让用户能及时发现输入与真实意图是否匹配，以及 Agent 是否理解有误。
- 复述应表达理解，不机械照抄原话，也不擅自增加用户未提出的要求。意图明确时，复述后直接继续，无须等待用户确认；只有存在会影响范围、授权或结果的关键歧义时才提出具体问题。用户更正后，按更正后的理解调整后续工作。
- 先理解问题、代码和约束，再提出方案或修改代码；区分已确认的事实和待验证的假设。
- **回答或解决问题前，先搜集足够信息，不可想当然的假设。**
- 独立判断用户方案的合理性；发现错误时，直接说明依据和影响。
- 用户询问某个方案是否合理时，先回答问题，不自动实施该方案。
- 对设计选择给出理由；证据表明判断有误时，及时修正。
- 在已授权范围内持续推进；关键信息缺失且会影响范围或结果时，提出具体问题。
- 完成用户任务所需的非破坏性操作可以自主执行，无须逐项征求授权；遵循用户明确限制和适用的权限要求。
- 用户未指定下一步时，可以结合项目目标提出优先级建议，不自行开始新的开发任务。
- 不主动重构无关代码，不覆盖或回滚用户已有改动。
- 文档引用使用相对于项目根目录的路径，必要时附行号和版本依据，便于复核。
- 流程投入与任务风险相称，不为了满足流程生成没有实质内容的文档。

## 开始任务前

### 优先阅读顺序

**开始每项任务时，必须首先检查项目根目录的 `GOAL.md`；若存在，读取全文并理解用户目标，再展开其他项目调研、方案分析或修改。** 文件不存在时继续任务，不因此阻塞，也不擅自补建。

完成目标检查后，按以下要求恢复上下文；已加载的适用规范始终有效，进入子目录前确认是否有局部 `AGENTS.md`。

1. **强烈推荐阅读根目录 `README.md`**，尤其在首次进入项目、不了解项目用途或恢复上下文时，先理解使用者能够做什么，以及项目的基本运行方式。
2. **开始开发任务或恢复项目上下文时，必须阅读 `docs/README.md`（若存在），并阅读全文其中标记为“常驻必读”的文档。** 将总体设计、架构边界和长期约束纳入本次分析与实施；只读目录不等于读过设计。上下文丢失后重新读取，不能仅凭此前读过就跳过。
3. 根据本次任务，从总入口按需阅读交接、计划和结果、专题设计、已知问题及待办等内容，再结合实际代码、配置、测试和 Git 记录核实。涉及已知问题或后续改进时先读相关主索引，再打开详情；历史条目仅在查重或追溯时读取。

总入口缺失时，从现有开发文档中定位与任务相关的总体设计和架构约束，不因此忽略重要设计；需要维护开发文档时按上述规则补建入口。缺失文档不阻塞任务，也不构成创建 `GOAL.md` 或空文档的授权。除必读内容外，其余上下文按任务相关性和变更情况补读，无须每次遍历整个仓库；文档可能过时，应结合当前实现核实。

### 新项目启动

1. 结合用户当前要求和已有目标，明确项目用途、本次交付范围与完成标准；只有会影响范围或结果的关键信息缺失时才提问。“开始项目”不构成创建或修改 `GOAL.md` 的授权。
2. 检查现有目录、文件和配置；已有 Git 仓库时检查当前分支及 `git status`，确认已有改动。目录中有内容时先判断是否为已有项目，保留用户文件，避免重复初始化或覆盖。
3. 确定首个可运行、可验证的交付，优先沿用已有技术和工具约定；没有约定时，依据需求选择并说明关键理由。按“计划和结果”的条件判断是否需要计划，需要时在工程初始化或实施前完成计划与自查。
4. 只搭建当前交付所需的工程结构、依赖和配置，打通必要的运行与验证流程；其余目录和文档按需创建，不预先铺设空壳。
5. 完成首个交付并进行相应验证。根目录 `README.md` 说明项目用途、安装和使用方法；开发环境、构建与测试方法及开发文档导航写入 `docs/README.md`。已有重要总体设计时登记为常驻必读；命令以实际配置为依据，尚未验证的步骤明确标注，任务结果按下文要求报告。

### 接手已有项目

1. 按优先阅读顺序恢复上下文，检查当前分支、`git status` 和已有改动；尚未使用 Git 时如实说明，通过现有文件确认项目状态，不假定工作区为空。
2. 结合交接文档、相关索引和当前计划核实进度，区分已完成、待验证和未完成事项。历史建议、TODO 或交接中的“下一步”不自动成为本次开发授权；已有明确任务时继续推进该任务。
3. 通过根目录 `README.md` 理解使用方式，对照 `docs/README.md` 和实际配置找到开发、构建及验证入口，按本次任务需要建立验证基线；发现已有失败时，记录复现条件，区分已有问题与本次改动引入的问题。
4. 定位相关模块、入口和测试，确认任务范围与验证方式后，再按计划要求实施。用户仅要求了解项目时，完成理解说明并给出有依据的下一步建议。

### 修改前确认

修改前明确任务范围、涉及文件、相关已有改动和验证方式。简单任务只读取相关上下文，无须遍历整个仓库。

## 文档命名和来源

- `<topic>`、`<tag>` 使用简短、可辨识的名称，单词间用 `-` 分隔。
- `<model>` 使用环境明确提供的实际模型 ID，统一小写，文件名不安全字符替换为 `-`；不得猜测模型名称或版本。
- 无法确定模型 ID 时使用 `model-unknown`，正文说明已知模型信息和未知项。
- PLAN 和 REVIEW 文件名必须包含创建文档的模型标识；后续换模型更新同一文件时保留原文件名，在正文记录更新者和时间。
- `<revision>` 使用所分析提交的前 8 位哈希；分析范围包含未提交或未跟踪内容，或仓库尚无提交时，使用 `WORKTREE`。
- 文档开头记录创建时间、实际模型信息和分析范围；涉及代码结论时记录完整提交哈希。使用 `WORKTREE` 时，记录基准提交（如有）以及相关未提交或未跟踪文件，说明内容尚未固定为提交。
- `GOAL.md` 使用固定文件名和上述简洁目标格式，不要求时间、模型或分析版本等元信息；文档整理规则不得作为擅自修改它的依据。
- 开发文档总入口和设计索引使用固定文件名，侧重当前导航，不要求模型和分析版本等元信息；总体设计正文仍按上述规则保留来源依据。
- KNOWN-ISSUES 和 TODOS 的详情保留创建时的文件头，后续来源、版本和状态按事件追加；索引仅汇总条目，不重复保存详情中的完整来源记录。
- 新建非固定入口文档遇到同名时追加数字后缀，不覆盖已有文档；固定入口已存在时按其职责更新，保留原有引用关系，`GOAL.md` 仍须遵循其专门授权规则。

## 已知问题与后续改进（KNOWN-ISSUES / TODOS）

### 用途和写入时机

两类文档保存跨任务仍需关注的事项，按以下边界分类：

- **KNOWN-ISSUES 记录当前已确认的问题**：缺陷、行为异常，以及影响既有功能使用的已知限制。说明现有行为哪里有问题、何时触发和有什么影响；以代码、复现结果或其他可核实证据为依据。
- **TODOS 记录后续希望推进的工作**：新功能、优化、重构、工具和文档改进。说明希望达到的目标、价值和完成标准；应来自用户提出的后续工作、明确延期的事项，或有当前代码依据且目标明确的改进建议。未经确认的建议标记为“待评估”，不自动视为已承诺的任务。
- 判断缺陷时以已有行为承诺和明确约束为依据。例如，承诺重连后消息不丢失却实际丢失，属于 KNOWN-ISSUES；增加尚未承诺的自动重连功能，属于 TODOS。

用户明确要求记录问题或待办时，按上述分类写入。在已授权开发或项目文档维护任务中，发现与当前任务相关、满足上述条件且任务结束后仍需跟踪的事项时，必须新增或更新对应记录，并在任务结束时说明。

- 纯问答和只读 Review 默认在回复中说明；用户明确要求记录后再写入文件。
- 未证实的猜测作为待验证项留在研究、Review 或回复中，不写成已知问题。当前任务中的临时步骤及已解决的一次性问题留在计划、结果或回复中，不机械新增长期条目；已有条目必须追加处理结果，用户明确要求保留记录时按其要求执行。
- 新建前检查当前及历史索引，同一事项只维护一个主体条目。已知缺陷的修复在 KNOWN-ISSUES 条目中关联计划，不再复制为 TODO；更大范围的改进涉及多个问题时，TODO 引用相应问题 ID。
- 计划、结果和交接文档保留必要摘要并引用条目 ID 和路径，避免另维护一份问题或待办清单。记录事项、调整索引和标注状态均不代表获得修复或开发授权；提交和推送遵循下文 Git 规则。

### 目录和编号

- 已知问题详情：`<KNOWN-ISSUES 详情目录>/KI-YYYYMMDD-HHmm-NNN-<topic>.md`。
- 后续改进详情：`<TODOS 详情目录>/TD-YYYYMMDD-HHmm-NNN-<topic>.md`。
- 时间取创建时的 Asia/Shanghai 时间；`NNN` 在两类条目各自同一分钟内从 `001` 递增，创建前检查已有编号。条目 ID 为不含 `<topic>` 和扩展名的部分，例如 `KI-20261012-1530-001`。
- 一个事项对应一个详情文件。ID 和文件名创建后保持稳定，状态、标题或 commit 变化时不改名、不另建替代文件。目录、主索引和历史索引均按需创建，不预先生成空文件。

### 详情只追加，索引维护当前状态

- **详情采用 append-only**：创建后仅在文件末尾追加带时间的事件，不删除、覆盖或重排既有记录。补充证据、更正结论、调整范围、优先级和状态都追加事件；更正时指出被更正记录及原因。
- 每个事件记录时间、实际模型信息、事件内容和依据；涉及代码结论时记录对应版本。状态变化记录原状态、新状态和原因；更换模型不改文件名，按“文档命名和来源”记录实际更新者。
- 创建记录必须包含 ID、标题、初始状态和来源。KNOWN-ISSUES 还包含问题描述、触发条件、影响、确认依据及临时绕过方式（如有）；TODOS 还包含目标、价值、范围、完成标准和优先级（如已确定）。后续按需追加关联计划、处理过程和验证结果。
- **主索引允许更新**，只保留用途、目录位置、当前条目及年度历史入口；每个当前条目一行，包含 ID、标题、当前状态、最后更新时间和详情链接，不堆积处理日志。索引注明项目根相对路径，Markdown 链接目标按索引所在目录解析，保证可打开。
- 更新时先追加详情，再同步索引。当前状态以详情中最后一次状态记录为准，最后更新时间取最后一个事件的时间；索引与详情不一致时依据详情修正，不能仅修改索引来改变状态。
- 已解决或误报的问题、已完成或取消的 TODO，在对应详情目录的 `archive-YYYY.md` 中按结束年份追加 ID、标题、结束状态、时间和详情链接，再从当前索引移除。历史索引保存结束时的快照，详情文件保持原路径。事项重开时在原详情追加状态记录，再恢复当前索引；不创建新 ID。

### commit 依据和完成状态

- 两类条目都必须记录建立时所参考代码版本的完整 commit hash，并注明需求、代码、Review 或其他来源。没有可用提交时如实说明；涉及未提交内容时标记 `WORKTREE`，记录基准提交及相关文件，不将基准 HEAD 描述为全部工作区内容的固定版本。
- KNOWN-ISSUES 区分发现或确认版本、引入提交和修复版本；引入提交只有定位并核实后才记录，未知时明确说明。TODO 的建立版本表示提出或分析工作时的代码基线，不表示工作已经实现。
- 解决问题或完成 TODO 时，追加处理结果、修复或实现版本、验证或验收结果及关联计划、结果文件（如有）。尚未提交时记录 `WORKTREE` 和基准提交；后续获得实际 commit 后追加其完整 hash，不为填写记录自动提交。
- 完成状态依据验证和完成标准判定，不能仅凭已有 commit 标记完成；未提交但已验证达到完成标准的工作可以标记完成，同时明确结果仍处于 `WORKTREE`。同样，存在绕过方式不等于问题已解决。
- KNOWN-ISSUES 状态：`未解决`、`处理中`、`已解决`、`接受限制`、`误报`。接受限制须注明决定依据，限制仍存在时保留在当前索引；误报须给出否定原结论的依据。问题复发时在原条目追加重开记录，恢复为未解决或处理中。
- TODOS 状态：`待评估`、`待实施`、`进行中`、`已完成`、`已取消`。延期或受阻通过事件说明原因及恢复条件；取消须记录原因，不描述为完成。任务恢复时在原条目追加记录，恢复为相应未完成状态。

## 计划和结果

多步骤、跨模块、改变用户可见行为，或涉及 API、数据结构、配置和数据库的实质修改，必须先建立计划。只读问答、Review、简单单文件局部修改和纯格式修正通常不需要计划；用户明确要求时按其要求执行。

计划命名：`<计划和结果目录>/PLAN-YYYYMMDD-NNN-<model>-<topic>.md`。`NNN` 为当天三位递增编号，创建前检查现有文件，避免冲突。

示例：`PLAN-20260915-001-gpt-6-astra-auth-flow.md`。

计划必须包含：

- 目标、范围和不在本次处理的事项
- 当前状态、依据和约束
- 实施步骤
- 验证方式和完成标准
- 主要风险及必要的回滚方式

实施前至少自查一次，检查设计缺陷、逻辑冲突和遗漏。范围或步骤发生实质变化时，先更新计划再实施。

使用了计划的任务，实施完成后必须在计划和结果目录生成对应结果文件，在计划文件的 `.md` 前追加 `-OUTCOME`，例如 `PLAN-20260915-001-gpt-6-astra-auth-flow-OUTCOME.md`。结果文件沿用计划文件名中的模型标识，正文记录实际执行模型、完成情况、计划偏差、验证结果和遗留问题。

在计划索引中按实际更新时间追加计划与结果文件的相对链接、状态和简要结果。索引不存在时按需创建；历史信息不完整时如实说明，不推测补写。

每完成一个计划，必须按下文 Git 规则为该计划的改动单独提交一次。

## 设计

总体设计使用固定入口，默认放在 `docs/design/OVERVIEW.md`，说明当前有效的系统职责、模块划分、关键交互、架构边界和主要取舍；项目已有稳定路径时沿用并在开发文档总入口登记，不为统一命名重复建档或迁移已有文档。

重要的总体设计和架构约束必须在 `docs/README.md` 中标记为“常驻必读”。在已授权范围内调整总体设计时，同步更新有效设计与相关入口，避免首页指向过时版本；具体设计内容和必读名单不写入 `AGENTS.md`。

专题设计文档按主题平铺在设计文档目录，命名为 `<topic>-YYYYMMDD-<tag>.md`，例如 `auth-20260915-overview.md`。总体设计固定入口和设计索引不套用专题文件名格式。

有设计文档时维护 `docs/design/INDEX.md`，按主题列出文档标题、用途、当前状态和相对链接，标明有效设计及替代关系；总入口链接设计索引。新增、调整或废弃设计文档时同步更新受影响的导航，不创建空索引。

涉及库、SDK、模块或对外 API 的重要设计时，明确使用场景、边界和兼容性要求，比较可行方案并说明取舍，定稿前至少复核一次。环境提供 `api-design-zh` skill 时使用；不可用时按上述要求完成设计并说明限制。

UI 设计也是设计文档的一部分，直接放在设计文档目录，简要说明页面、状态和交互范围。具体设计方法、视觉规范和验收要求遵循用户指定的 UI skill，默认参考 ui-design-zh 这个skill；未指定时沿用项目现有约定。

## 实施和验证

- 按已确定的范围和计划实施，优先复用项目现有模式和工具。
- 保留已有改动，提交时仅暂存本次任务的改动；同一文件包含用户改动时应区分处理。
- 不使用未经授权的破坏性操作，包括强制覆盖、批量删除和回滚用户改动。
- 完成修改后进行代码自查，修复本次引入的问题。
- 根据行为变化和风险，运行相关测试、构建、lint 或静态检查；涉及共享行为时扩大验证范围。
- 新增测试应覆盖实际风险和行为，不为简单文档、格式修改或重复实现逻辑而机械增加测试。
- 必要验证失败时先修复；无法完成验证时记录原因、影响和剩余风险，不将其报告为通过。

## Git 提交和推送

- 为完成用户任务需要时，可以自主执行 `commit` 和普通 `push`，无须分别征求明确授权；用户明确限制或禁止时遵循其要求。
- **默认每次 `commit` 成功后，必须立即完成下述推送前检查并执行普通 `push`，不等待后续任务或积攒多个提交。** 用户明确要求仅本地提交、暂缓或禁止推送时，遵循用户要求。
- 提交前检查当前分支、暂存区和验证结果，只包含本次授权范围内的改动。
- 必要验证失败或无法执行时，先报告具体情况；只有用户明确接受该状态后，才继续提交或推送。
- 提交前读取当前分支上一条 commit 的消息，提交消息默认沿用其语言；用户明确指定提交语言时遵循用户要求。没有 commit 记录且用户尚未指定语言时，必须先向用户询问并确认，再创建提交，不自行假定语言。
- 提交消息必须详细说明本次提交实际完成的工作：标题概括核心变更，正文以列表逐条写清具体改动、涉及的功能或模块及必要的原因。以本次暂存区的实际 diff 为依据，重点说明改了什么，不能只写计划目标、完成状态或计划和结果文件的名称、路径。
- 使用了计划时，提交消息必须包含计划及结果文件的相对路径，新增设计文档时注明其路径；这些引用只作为补充，不能代替对实际改动的逐条说明。
- 推送前检查远端、目标分支和待推送提交范围；发现范围外提交时先说明情况。
- 不自动使用强制推送；确有需要时必须获得用户对具体目标和操作的明确授权。
- 执行后报告 commit ID 和推送状态；推送受阻或失败时说明原因，保留本地提交，不将本地提交描述为已推送。
- 每完成一个计划，必须为该计划的本次改动单独提交一次；提交时遵循上述用户限制、验证和范围要求。

## 代码解释

- 用户要求解释代码或功能时，先阅读相关实现，围绕问题说明用途、入口、主要调用流程和关键逻辑，区分代码事实、推断和待验证项。
- 无论在回复中还是文件中输出，每项关键实现或功能行为的说明都必须指明对应文件路径和准确行号，例如 `src/auth.ts:42`；跨文件流程分别标注关键环节的代码依据，行号以实际读取的版本为准，不得猜测。
- **默认直接在回复中解释；只有用户明确要求输出到文件时，才创建或修改解释文档。** 未要求写文件时，不创建代码解释目录，也不将解释另存为侦察文档或其他文件。
- 要求写文件时，默认命名为 `<代码解释目录>/{YYYYMMDD-HH}-{TOPIC}-{COMMIT-ID}.md`，目录按需创建；用户明确指定路径或文件名时遵循其要求。
- `{YYYYMMDD-HH}` 取文档创建时的 Asia/Shanghai 时间，文件名精确到小时，`HH` 使用 24 小时制；正文时间仍精确到分钟。`{TOPIC}` 使用简短、可辨识的主题名称，单词间用 `-` 分隔。
- `{COMMIT-ID}` 使用所解释代码对应提交的前 8 位哈希；解释范围包含未提交或未跟踪内容，或仓库尚无提交时，使用 `WORKTREE`。文档中的完整提交哈希、基准提交和相关未提交文件等来源信息遵循“文档命名和来源”规则；新建文件重名时追加数字后缀，不覆盖已有文档。

命名示例：`docs/explanations/20261016-10-auth-flow-a1b2c3d4.md`。

## 侦察文档

侦察文档用于记录代码研究结果，说明研究问题、已确认的事实、文件路径和行号依据，以及尚未确认的问题。

命名：`<侦察文档目录>/YYYYMMDD-HHmm-RESEARCH-<revision>-<topic>.md`。来源信息遵循“文档命名和来源”规则。

## Review

- 用户要求 Review 时，默认在回复中给出结果；只有明确要求形成文档时才写入文件。
- 优先关注缺陷、行为回归、规则冲突和缺失的验证，按严重性排序。
- 每条发现说明触发条件、影响和代码或文档依据，给出必要的修正建议；不把个人风格偏好当作缺陷。
- 没有发现问题时明确说明，同时指出相关验证空白或剩余不确定性。
- Review 请求本身不授权修改被审查内容；用户同时要求修复时再实施。

Review 文档命名：`<Review 文档目录>/YYYYMMDD-HHmm-REVIEW-<model>-<revision>-<topic>.md`。

示例：`20260915-1200-REVIEW-gpt-6-astra-WORKTREE-auth-flow.md`。

用户要求复核已有 Review 时，逐条核实并说明依据；需要输出文档时，在原文件的 `.md` 前追加 `-review-verification-<model>`，保留原目录，正文记录本次复核的实际版本。此处 `<model>` 为复核模型，例如 `20260915-1200-REVIEW-gpt-6-astra-WORKTREE-auth-flow-review-verification-gpt-5.6-terra.md`。

## 逆向功能规格说明书（RFS）

用户要求生成 RFS 时，默认覆盖整个仓库；指定模块时只覆盖指定范围。RFS 基于代码恢复现有行为，区分代码事实和未知项，不把改进建议写成现有功能。

内容应覆盖用户可见行为、输入输出、数据边界、状态变化、异常处理、权限配置和外部交互，并提供对应代码依据。

命名：`<逆向功能规格说明书目录>/YYYYMMDD-HHmm-RFS-<revision>-<topic>.md`。

完成后至少复核一次，以不了解原代码的团队能够据此实现行为一致的替代品为目标；对无法从代码确认的外部依赖和运行时行为，明确记录待验证项。

## 交接文档

用户明确要求，或未完成的长任务需要暂停、资源限制影响继续执行时，更新交接文档。不得猜测无法获取的剩余额度。

交接内容包括项目背景、已完成工作、工作区状态、已知问题、待办和建议的下一步，以及相关文档、代码路径和 commit ID。区分已验证结论与假设，让接手者能够继续工作。

## 任务结束时

简要说明完成内容、关键文件、验证结果和未完成事项；执行了提交或推送时报告实际状态。问题解决后结束，不追加无关任务，也不重复索要已经获得的授权。
