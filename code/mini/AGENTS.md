# Agent 工作规范

本文件适用于所在目录及其子目录；需要约束整个仓库时，应放在仓库根目录。以下文档路径均相对于项目根目录。

## 规则优先级

- 遵循系统、开发者和用户指令，本文件不得覆盖更高优先级的指令；用户在本次会话中明确给出的授权和约束持续有效，无须重复确认。
- “必须”“应该”“可以”分别表示 MUST、SHOULD、MAY；对用户意图的推断只是工作假设，不能用于扩大范围或违反用户约束。

## 项目配置

- 项目目标（用户意图）：`./GOAL.md`，位于项目根目录。
- 交接文档：`docs/HANDOFF.md`
- 项目说明文档：`README.md`
- KNOWN-ISSUES 索引：`docs/KNOWN-ISSUES.md`
- KNOWN-ISSUES 详情目录：`docs/known-issues/`
- TODOS 索引：`docs/TODOS.md`
- TODOS 详情目录：`docs/todos/`
- 设计文档目录：`docs/design/`
- 侦察文档目录：`docs/research/`
- 代码解释目录：`docs/explanations/`
- 计划和结果目录：`docs/plans/`
- 计划索引：`docs/plans/INDEX.md`
- Review 文档目录：`docs/reviews/`
- 逆向功能规格说明书目录：`docs/reverse-spec/`
- 文档目录、`AGENTS.md` 和 `GOAL.md` 纳入版本管理；提交和推送遵循下文 Git 规则。
- Git commit 消息、文档和注释使用中文；代码标识符、命令和专有名词保留原文。
- 文档时间使用 Asia/Shanghai 时区，精确到分钟。

目录和文档按需创建，不预先生成空文件。

## 项目目标和工作原则

- 开始每项任务时，必须先检查项目根目录的 `GOAL.md`；存在则全文阅读，再进行项目调研、分析或修改。不存在时继续任务，不擅自创建。
- `GOAL.md` 简洁记录用户目标和大致功能范围，不记录实施步骤、进度或待办。只有用户明确要求创建或修改项目目标文件时，才按指定范围操作；否则不得创建、修改、追加、重命名或删除。代码、新需求或任务状态变化不构成授权；用户当前指令优先于旧目标。
- 先收集足够信息，理解问题、代码和约束，区分事实、推断与待验证项；独立判断方案，说明依据，发现错误及时纠正。用户询问方案是否合理时先回答，不自动实施。
- 在授权范围内持续推进，完成任务所需的非破坏性操作无须逐项确认；关键信息缺失且影响范围或结果时，提出具体问题。用户未指定下一步时可提出建议，不自行开始新开发任务。
- 按需检查 Git 状态、项目文档、相关代码和历史，结合代码核实文档；修改前明确范围、已有改动及验证方式。涉及问题或待办时先查相关索引，按需阅读详情。
- 不重构无关代码，不覆盖或回滚用户改动；流程与风险相称，不生成没有实质内容的文档。文档引用使用项目根目录相对路径，必要时附行号和版本依据。

## 文档命名和来源

- `<topic>`、`<tag>` 使用简短、可辨识的名称，单词间用 `-` 分隔。`<model>` 使用环境明确提供的实际模型 ID，小写并将文件名不安全字符替换为 `-`；无法确定时使用 `model-unknown` 并在正文说明，不猜测。
- `<revision>` 使用所分析提交的前 8 位哈希；分析范围包含未提交或未跟踪内容，或仓库尚无提交时使用 `WORKTREE`。文档开头记录创建时间、实际模型信息和分析范围；涉及代码结论时记录完整 commit hash。使用 `WORKTREE` 时记录基准提交（如有）及相关未提交或未跟踪文件。
- PLAN 和 REVIEW 文件名包含创建文档的模型标识，后续更新保留原文件名并记录更新者和时间。新文件重名时追加数字后缀，不覆盖已有文档；更新时保留引用关系。
- `GOAL.md` 不要求以上元信息；问题与待办详情保留创建时的文件头，后续来源、版本和状态按事件追加。

## 已知问题与后续改进

- KNOWN-ISSUES 记录有证据确认的缺陷、异常及影响既有功能的限制；TODOS 记录后续功能、优化、重构、工具或文档工作，须来自用户、明确延期事项或有当前代码依据且目标明确的建议。未经确认的建议标为“待评估”，不视为已承诺；未证实的猜测不写成已知问题。
- 用户要求记录时，或在已授权开发、项目文档维护中发现与当前任务相关且结束后仍需跟踪的事项时，新增或更新记录并在结束时说明。纯问答和只读 Review 默认只在回复中说明，除非用户明确要求记录；临时步骤和已解决的一次性问题不机械建条目，已有条目须追加处理结果。
- 新建前检查当前及历史索引，同一事项只维护一个详情文件；缺陷修复关联问题条目而不复制为 TODO，较大改进涉及多个问题时引用相关问题 ID。计划、结果和交接只保留必要摘要并引用条目 ID 和路径；记录事项不代表获得修复或开发授权。
- 详情分别命名为 `<KNOWN-ISSUES 详情目录>/KI-YYYYMMDD-HHmm-NNN-<topic>.md` 和 `<TODOS 详情目录>/TD-YYYYMMDD-HHmm-NNN-<topic>.md`。时间取创建时的 Asia/Shanghai 时间，`NNN` 按类别在同一分钟内从 `001` 递增；不含主题和扩展名的部分为 ID。ID、文件名和详情路径创建后保持不变。
- 创建记录包含 ID、标题、状态、来源和所依据的完整 commit hash；无提交时说明，涉及工作区改动时注明 `WORKTREE`、基准提交及相关文件。问题还须记录描述、触发条件、影响、确认依据和可用的绕过方式；TODO 记录目标、价值、范围、完成标准及已确定的优先级。
- 详情创建后只在末尾追加事件，不删除、覆盖或重排；事件记录时间、实际模型、内容和依据，涉及代码时注明版本，状态变化说明原状态、新状态及原因。更正结论时指出原记录和原因。
- 更新时先追加详情，再同步主索引。当前状态以详情最后一次状态记录为准；索引每项一行，只保留 ID、标题、状态、最后事件时间和详情链接，以及用途、目录和年度历史入口。索引注明项目根相对路径，Markdown 链接按索引所在目录解析。
- 已解决或误报的问题、已完成或取消的 TODO，按结束年份追加到详情目录的 `archive-YYYY.md`，记录 ID、标题、结束状态、时间和链接，再从当前索引移除；重开时在原详情追加记录并恢复索引，不新建 ID。
- 问题状态：`未解决`、`处理中`、`已解决`、`接受限制`、`误报`；接受限制须说明依据且限制仍存在时保留在当前索引，误报须说明否定依据，复发时恢复为未解决或处理中。TODO 状态：`待评估`、`待实施`、`进行中`、`已完成`、`已取消`；延期或受阻记录原因和恢复条件，取消记录原因，恢复时回到相应未完成状态。
- 完成以验证和完成标准为依据，不能仅凭已有 commit 或问题绕过方式认定完成；追加处理结果、版本、验证结果及相关计划和结果文件（如有）。未提交但已验证的工作可完成，须标记 `WORKTREE`，获得实际 commit 后追加完整 hash。问题的发现、引入和修复版本须区分；引入提交未经核实则注明未知，不为填记录自动提交。

## 计划、设计与实施

- 多步骤、跨模块、改变用户可见行为，或涉及 API、数据结构、配置、数据库的实质修改，必须先建立计划；只读问答、Review、简单单文件局部修改和纯格式修正通常不需要，用户另有要求时遵循其要求。
- 计划命名为 `<计划和结果目录>/PLAN-YYYYMMDD-NNN-<model>-<topic>.md`，`NNN` 为当天三位递增编号，创建前检查已有文件。写明目标、范围及不处理事项、现状、依据和约束、步骤、验证和完成标准、风险及必要的回滚方式；实施前至少自查一次设计缺陷、逻辑冲突和遗漏，实质调整时先更新计划。
- 使用计划的任务完成后，在计划文件名的 `.md` 前追加 `-OUTCOME` 创建结果文件，记录实际执行模型、完成情况、偏差、验证和遗留问题；在计划索引中按实际更新时间追加计划及结果的相对链接、状态和简要结果，历史信息不完整时不推测补写。每完成一个计划，必须按下文 Git 规则单独提交一次。
- 设计文档平铺于设计文档目录，命名为 `<topic>-YYYYMMDD-<tag>.md`。重要的库、SDK、模块或对外 API 设计须说明场景、边界和兼容性，比较方案、说明取舍并在定稿前复核；可用时使用 `api-design-zh` skill，不可用时按上述要求完成并说明。UI 设计说明页面、状态及交互范围，遵循用户指定的 UI skill；未指定时参考可用的 `ui-design-zh` 和项目约定。
- 按范围和计划实施，优先复用现有模式和工具；不执行未经授权的破坏性操作。完成后自查，并按风险运行相关测试、构建、lint 或静态检查，共享行为扩大验证范围。测试应覆盖实际风险，不为简单文档、格式或重复实现机械增加测试；验证失败先修复，无法验证时说明原因和风险，不报告为通过。

## Git 提交和推送

- 每完成一个计划，必须为该计划的本次改动单独提交一次；为完成任务需要时，可自主 commit 和普通 push。遵循用户明确限制；提交前检查分支、暂存区和验证结果，只提交本次授权改动，同一文件含用户改动时区分处理；消息说明变更和原因，并注明所用计划、结果和新增设计文档的相对路径。
- 必要验证失败或无法执行时先报告具体情况，仅在用户明确接受后提交或推送。推送前检查远端、目标分支和待推送提交范围，发现范围外提交先说明；强制推送须获得用户对具体目标和操作的明确授权。
- 执行后报告 commit ID 和推送状态，不把本地提交描述为已推送。

## 代码解释、侦察与 Review

- 解释代码或功能前先阅读实现；说明用途、入口、调用流程和关键逻辑，区分事实、推断和未知项。每项关键实现或行为均给出实际版本对应的文件路径和准确行号，跨文件流程分别标注，不得猜测行号。
- 代码解释默认直接回复，只有用户明确要求输出到文件时才写入，默认命名为 `<代码解释目录>/YYYYMMDD-HH-<topic>-<revision>.md`；未要求写文件时不得另存为其他文档。文件名时间精确到小时并使用 24 小时制，正文仍精确到分钟；用户指定路径时遵循其要求。
- 侦察文档记录研究问题、已确认事实、路径和行号依据及未确认项，命名为 `<侦察文档目录>/YYYYMMDD-HHmm-RESEARCH-<revision>-<topic>.md`。
- Review 默认直接回复，只有明确要求时才写文件；按严重性报告缺陷、回归、规则冲突和验证缺口，并说明触发条件、影响、依据及必要的修正建议，不把风格偏好当缺陷。无发现时明确说明，并指出验证空白或剩余不确定性。Review 本身不授权修改，用户同时要求修复时再实施。
- Review 文档命名为 `<Review 文档目录>/YYYYMMDD-HHmm-REVIEW-<model>-<revision>-<topic>.md`。复核已有 Review 时逐条核实；要求输出文件时，在原文件名的 `.md` 前追加 `-review-verification-<model>`，使用本次复核模型并在正文记录复核版本。

## 逆向功能规格与交接

- 用户要求生成 RFS 时，默认覆盖整个仓库；指定模块时按指定范围。基于代码记录现有行为及依据，覆盖用户可见行为、输入输出、数据边界、状态、异常、权限配置和外部交互，区分事实与未知项，不把建议写成现有功能。
- RFS 命名为 `<逆向功能规格说明书目录>/YYYYMMDD-HHmm-RFS-<revision>-<topic>.md`；完成后至少复核一次，以可据此实现行为一致的替代品为目标，未确认的外部依赖和运行时行为标为待验证。
- 用户明确要求，或未完成的长任务需要暂停、资源限制影响继续执行时，更新交接文档。记录背景、已完成工作、工作区状态、问题、待办、建议下一步及相关路径和 commit ID，区分已验证结论与假设，不猜测无法获取的剩余额度。

## 任务结束时

简要说明完成内容、关键文件、验证结果和未完成事项；有提交或推送时报告实际状态。任务结束后不追加无关工作，不重复索要已获得的授权。
