# Agent 工作规范（条文版）

## 第一章 总则

### 第一条【适用范围】

本规范适用于本文件所在目录及其子目录。需要约束整个仓库时，应当将本文件放在仓库根目录。除另有说明外，本规范中的文档路径均相对于项目根目录。

### 第二条【指令优先级】

Agent 必须遵循系统、开发者和用户指令，不得以本规范覆盖更高优先级的指令。

用户在本次会话中明确给出的授权和约束持续有效，无须重复确认。对用户意图的推断属于工作假设，不得据此扩大任务范围或者违反用户约束。

### 第三条【规范用语】

本规范中的“必须”“应当”表示强制性要求（MUST），“不得”表示禁止性要求（MUST NOT），“应该”表示建议（SHOULD），“可以”表示允许（MAY）。

## 第二章 项目配置与目标

### 第四条【项目路径】

项目配置如下：

（一）项目目标：`./GOAL.md`，位于项目根目录。

（二）交接文档：`docs/HANDOFF.md`。

（三）KNOWN-ISSUES 索引：`docs/KNOWN-ISSUES.md`；详情目录：`docs/known-issues/`。

（四）TODOS 索引：`docs/TODOS.md`；详情目录：`docs/todos/`。

（五）项目说明文档：`README.md`。

（六）设计文档目录：`docs/design/`。

（七）侦察文档目录：`docs/research/`。

（八）代码解释目录：`docs/explanations/`。

（九）计划和结果目录：`docs/plans/`；计划索引：`docs/plans/INDEX.md`。

（十）Review 文档目录：`docs/reviews/`。

（十一）逆向功能规格说明书目录：`docs/reverse-spec/`。

文档目录、`AGENTS.md` 和 `GOAL.md` 应当纳入版本管理；提交和推送依照本规范第七章执行。目录和文档按需创建，不得预先生成空文件。

### 第五条【语言、时间与引用】

Git commit 消息、文档和注释使用中文；代码标识符、命令和专有名词保留原文。文档时间使用 Asia/Shanghai 时区，精确到分钟；本规范对文件名时间另有规定的，从其规定。

文档引用使用相对于项目根目录的路径，必要时附行号和版本依据。Markdown 链接目标按照链接所在文件的目录解析。

### 第六条【项目目标】

`GOAL.md` 表达用户希望项目实现的目标及大致功能范围；`AGENTS.md` 约束 Agent 的工作方式。分析、设计和实施应当以目标与规范共同确定的方向和边界为依据，并遵循指令优先级。

`GOAL.md` 可以只有一句话，也可以是一句话加粗略功能列表；其内容应当简洁，不得混入实施步骤、任务进度或者待办清单。

只有用户明确要求创建或者修改项目目标文件时，才允许按指定范围操作 `GOAL.md`。未获此类要求，不得创建、修改、追加、重命名或者删除该文件；一般开发、文档整理以及目标相关功能的实现均不构成修改授权。

代码现状、新需求、计划、TODO 或者任务完成状态的变化，均不触发自动更新。Agent 可以在回复中提出目标调整建议，不得自行写入。用户当前明确指令优先于文件中的旧目标；执行新指令不意味着获得更新 `GOAL.md` 的授权，不得用代码现状自行替换或者缩减用户目标。

### 第七条【任务开始前的检查】

开始每项任务时，Agent 必须首先检查项目根目录的 `GOAL.md`；文件存在的，应当阅读全文并理解用户目标，再展开其他项目调研、方案分析或者修改。文件不存在的，继续任务，不因此阻塞，也不得擅自补建。

Agent 应当按需检查 `git status`、目录结构、项目说明、交接文档、相关设计和计划、代码与提交历史，并结合当前代码和 Git 记录核实可能过时的文档。

涉及已知问题或者后续改进的，应当先读取相关主索引，再按需打开详情；历史条目仅在查重或者追溯时读取。修改前应当明确任务范围、涉及文件、相关已有改动和验证方式；简单任务只需读取相关上下文，无须遍历整个仓库。

### 第八条【基本工作原则】

回答或者解决问题前，Agent 应当收集足够信息，理解问题、代码和约束，区分已确认事实与待验证假设，不得想当然地假设。

Agent 应当独立判断用户方案；发现错误时，直接说明依据和影响。用户询问方案是否合理的，应当先回答，不自动实施。对设计选择应当给出理由；证据表明判断有误时，应当及时修正。

Agent 应当在已授权范围内持续推进；完成用户任务所需的非破坏性操作可以自主执行，无须逐项征求授权，但应当遵循用户明确限制和适用的权限要求。关键信息缺失且影响范围或者结果的，应当提出具体问题。

用户未指定下一步时，Agent 可以结合项目目标提出优先级建议，不自行开始新的开发任务。Agent 不得主动重构无关代码，不得覆盖或者回滚用户已有改动。流程投入应当与任务风险相称，不得为了满足流程生成没有实质内容的文档。

## 第三章 文档命名与来源

### 第九条【名称与模型标识】

`<topic>`、`<tag>` 使用简短、可辨识的名称，单词间以 `-` 分隔。`<model>` 使用环境明确提供的实际模型 ID，统一小写，并将文件名不安全字符替换为 `-`；不得猜测模型名称或者版本。

无法确定模型 ID 时，使用 `model-unknown`，并在正文说明已知模型信息和未知项。PLAN 和 REVIEW 文件名必须包含创建文档的模型标识；后续换模型更新同一文件时，保留原文件名，并在正文记录更新者和时间。

### 第十条【分析版本与来源】

`<revision>` 使用所分析提交的前 8 位哈希；分析范围包含未提交或者未跟踪内容，或者仓库尚无提交时，使用 `WORKTREE`。

文档开头应当记录创建时间、实际模型信息和分析范围；涉及代码结论的，应当记录完整提交哈希。使用 `WORKTREE` 时，应当记录基准提交（如有）以及相关未提交或者未跟踪文件，说明内容尚未固定为提交。

### 第十一条【例外与文件保护】

`GOAL.md` 使用固定文件名和第六条规定的简洁目标格式，不要求时间、模型或者分析版本等元信息；文档整理规则不得作为擅自修改该文件的依据。

KNOWN-ISSUES 和 TODOS 的详情应当保留创建时的文件头，后续来源、版本和状态按事件追加；索引仅汇总条目，不重复保存详情中的完整来源记录。

新建文件遇到同名时，应当追加数字后缀，不得覆盖已有文档；更新现有文档时，应当保留原有引用关系。

## 第四章 已知问题与后续改进

### 第十二条【分类】

KNOWN-ISSUES 记录当前已确认的缺陷、行为异常以及影响既有功能使用的已知限制；应当说明现有行为的问题、触发条件和影响，并以代码、复现结果或者其他可核实证据为依据。

TODOS 记录后续希望推进的新功能、优化、重构、工具和文档改进；应当说明目标、价值和完成标准，并来自用户提出的后续工作、明确延期的事项，或者有当前代码依据且目标明确的改进建议。未经确认的建议标记为“待评估”，不自动视为已承诺的任务。

判断缺陷时，应当以已有行为承诺和明确约束为依据。例如，承诺重连后消息不丢失而实际丢失的，属于 KNOWN-ISSUES；增加尚未承诺的自动重连功能，属于 TODOS。

### 第十三条【记录时机】

用户明确要求记录问题或者待办时，应当依照第十二条分类写入。在已授权开发或者项目文档维护任务中，发现与当前任务相关、符合第十二条条件且任务结束后仍需跟踪的事项时，必须新增或者更新对应记录，并在任务结束时说明。

纯问答和只读 Review 默认在回复中说明；用户明确要求记录后再写入文件。未证实的猜测作为待验证项留在研究、Review 或者回复中，不得写成已知问题。

当前任务的临时步骤及已解决的一次性问题，留在计划、结果或者回复中，不机械新增长期条目；已有条目必须追加处理结果。用户明确要求保留记录的，依照其要求执行。

### 第十四条【去重与授权边界】

新建条目前，应当检查当前及历史索引；同一事项只维护一个主体条目。已知缺陷的修复在 KNOWN-ISSUES 条目中关联计划，不再复制为 TODO；更大范围的改进涉及多个问题时，TODO 引用相应问题 ID。

计划、结果和交接文档保留必要摘要并引用条目 ID 和路径，避免另维护一份问题或者待办清单。记录事项、调整索引和标注状态，均不代表获得修复或者开发授权；提交和推送依照第七章执行。

### 第十五条【文件名与编号】

已知问题详情命名为 `<KNOWN-ISSUES 详情目录>/KI-YYYYMMDD-HHmm-NNN-<topic>.md`；后续改进详情命名为 `<TODOS 详情目录>/TD-YYYYMMDD-HHmm-NNN-<topic>.md`。

时间取创建时的 Asia/Shanghai 时间；`NNN` 在两类条目各自同一分钟内从 `001` 递增，创建前应当检查已有编号。条目 ID 为不含 `<topic>` 和扩展名的部分，例如 `KI-20261012-1530-001`。

一个事项对应一个详情文件。ID 和文件名创建后保持稳定，状态、标题或者 commit 变化时不改名、不另建替代文件；目录、主索引和历史索引按需创建。

### 第十六条【创建记录】

创建记录必须包含 ID、标题、初始状态和来源，并记录建立时所参考代码版本的完整 commit hash，注明需求、代码、Review 或者其他来源。没有可用提交时，应当如实说明；涉及未提交内容时，标记 `WORKTREE`，记录基准提交及相关文件，不得将基准 HEAD 描述为全部工作区内容的固定版本。

KNOWN-ISSUES 还应当包含问题描述、触发条件、影响、确认依据及临时绕过方式（如有）；TODOS 还应当包含目标、价值、范围、完成标准和优先级（如已确定）。后续按需追加关联计划、处理过程和验证结果。

### 第十七条【详情只追加】

详情创建后采用 append-only 方式，仅在文件末尾追加带时间的事件，不得删除、覆盖或者重排既有记录。补充证据、更正结论、调整范围、优先级和状态，均以追加事件的方式记录；更正时应当指出被更正记录及原因。

每个事件应当记录时间、实际模型信息、事件内容和依据；涉及代码结论时，应当记录对应版本。状态变化应当记录原状态、新状态和原因；更换模型不改文件名，并依照第九条记录实际更新者。

### 第十八条【主索引】

主索引可以更新，只保留用途、目录位置、当前条目及年度历史入口；每个当前条目一行，包含 ID、标题、当前状态、最后更新时间和详情链接，不堆积处理日志。索引应当注明项目根相对路径，Markdown 链接目标按索引所在目录解析，保证可打开。

更新时先追加详情，再同步索引。当前状态以详情最后一次状态记录为准，最后更新时间取最后一个事件的时间；索引与详情不一致时，应当依据详情修正，不得仅修改索引来改变状态。

### 第十九条【归档与重开】

已解决或者误报的问题、已完成或者取消的 TODO，应当在对应详情目录的 `archive-YYYY.md` 中按结束年份追加 ID、标题、结束状态、时间和详情链接，再从当前索引移除。历史索引保存结束时的快照，详情文件保持原路径。

事项重开时，应当在原详情追加状态记录，再恢复当前索引，不得创建新 ID。

### 第二十条【状态】

KNOWN-ISSUES 状态为 `未解决`、`处理中`、`已解决`、`接受限制`、`误报`。接受限制须注明决定依据，限制仍存在时保留在当前索引；误报须给出否定原结论的依据。问题复发时，在原条目追加重开记录，恢复为未解决或者处理中。

TODOS 状态为 `待评估`、`待实施`、`进行中`、`已完成`、`已取消`。延期或者受阻通过事件说明原因及恢复条件；取消须记录原因，不得描述为完成。任务恢复时，在原条目追加记录，恢复为相应未完成状态。

### 第二十一条【版本与完成依据】

KNOWN-ISSUES 应当区分发现或者确认版本、引入提交和修复版本；引入提交只有定位并核实后才记录，未知时应当明确说明。TODO 的建立版本表示提出或者分析工作时的代码基线，不表示工作已经实现。

解决问题或者完成 TODO 时，应当追加处理结果、修复或者实现版本、验证或者验收结果，以及关联计划、结果文件（如有）。尚未提交时，记录 `WORKTREE` 和基准提交；后续获得实际 commit 后追加其完整 hash，不为填写记录自动提交。

完成状态依据验证和完成标准判定，不得仅凭已有 commit 标记完成；未提交但已验证达到完成标准的工作可以标记完成，同时明确结果仍处于 `WORKTREE`。存在绕过方式不等于问题已解决。

## 第五章 计划与设计

### 第二十二条【计划的建立】

多步骤、跨模块、改变用户可见行为，或者涉及 API、数据结构、配置和数据库的实质修改，必须先建立计划。只读问答、Review、简单单文件局部修改和纯格式修正通常不需要计划；用户明确要求时，依照其要求执行。

计划命名为 `<计划和结果目录>/PLAN-YYYYMMDD-NNN-<model>-<topic>.md`。`NNN` 为当天三位递增编号，创建前应当检查现有文件，避免冲突。

### 第二十三条【计划内容与复核】

计划必须包含下列内容：

（一）目标、范围和不在本次处理的事项；

（二）当前状态、依据和约束；

（三）实施步骤；

（四）验证方式和完成标准；

（五）主要风险及必要的回滚方式。

实施前至少自查一次，检查设计缺陷、逻辑冲突和遗漏。范围或者步骤发生实质变化时，应当先更新计划再实施。

### 第二十四条【结果与计划索引】

使用了计划的任务，实施完成后必须在计划和结果目录生成对应结果文件，在计划文件的 `.md` 前追加 `-OUTCOME`。结果文件沿用计划文件名中的模型标识，正文记录实际执行模型、完成情况、计划偏差、验证结果和遗留问题。

在计划索引中按实际更新时间追加计划与结果文件的相对链接、状态和简要结果。索引不存在时按需创建；历史信息不完整时如实说明，不推测补写。每完成一个计划，必须依照第二十八条为该计划的改动单独提交一次。

### 第二十五条【设计文档】

所有设计文档按主题平铺在设计文档目录，命名为 `<topic>-YYYYMMDD-<tag>.md`。

涉及库、SDK、模块或者对外 API 的重要设计，应当明确使用场景、边界和兼容性要求，比较可行方案并说明取舍，定稿前至少复核一次。环境提供 `api-design-zh` skill 时使用；不可用时，按上述要求完成设计并说明限制。

UI 设计属于设计文档的一部分，直接放在设计文档目录，简要说明页面、状态和交互范围。具体设计方法、视觉规范和验收要求遵循用户指定的 UI skill，默认参考 `ui-design-zh` skill；未指定时沿用项目现有约定。

## 第六章 实施与验证

### 第二十六条【实施】

Agent 应当按已确定的范围和计划实施，优先复用项目现有模式和工具。应当保留已有改动；不得使用未经授权的破坏性操作，包括强制覆盖、批量删除和回滚用户改动。

完成修改后，应当进行代码自查，修复本次引入的问题。

### 第二十七条【验证】

Agent 应当根据行为变化和风险，运行相关测试、构建、lint 或者静态检查；涉及共享行为时扩大验证范围。

新增测试应当覆盖实际风险和行为，不得为简单文档、格式修改或者重复实现逻辑而机械增加测试。必要验证失败时应当先修复；无法完成验证时，应当记录原因、影响和剩余风险，不得将其报告为通过。

## 第七章 Git 提交与推送

### 第二十八条【提交授权与计划提交】

为完成用户任务需要时，可以自主执行 `commit` 和普通 `push`，无须分别征求明确授权；用户明确限制或者禁止时，遵循其要求。

每完成一个计划，必须为该计划的本次改动单独提交一次；提交时应当遵循用户限制及本章规定的验证和范围要求。

### 第二十九条【提交条件】

提交前，应当检查当前分支、暂存区和验证结果，只暂存并提交本次授权范围内的改动；同一文件包含用户改动时，应当区分处理。

必要验证失败或者无法执行时，应当先报告具体情况；只有用户明确接受该状态后，才继续提交或者推送。

提交消息应当说明变更和原因；使用了计划时，必须包含计划及结果文件的相对路径；新增设计文档时，应当注明其路径。

### 第三十条【推送与报告】

推送前，应当检查远端、目标分支和待推送提交范围；发现范围外提交时，应当先说明情况。

不得自动使用强制推送；确有需要时，必须获得用户对具体目标和操作的明确授权。执行提交或者推送后，应当报告 commit ID 和推送状态，不得将本地提交描述为已推送。

## 第八章 专项文档与输出

### 第三十一条【代码解释】

用户要求解释代码或者功能时，应当先阅读相关实现，围绕问题说明用途、入口、主要调用流程和关键逻辑，区分代码事实、推断和待验证项。

无论在回复中还是文件中输出，每项关键实现或者功能行为的说明都必须指明对应文件路径和准确行号，例如 `src/auth.ts:42`；跨文件流程分别标注关键环节的代码依据，行号以实际读取的版本为准，不得猜测。

代码解释默认直接在回复中输出；只有用户明确要求输出到文件时，才创建或者修改解释文档。未要求写文件时，不创建代码解释目录，也不得将解释另存为侦察文档或者其他文件。

### 第三十二条【代码解释文档命名】

用户要求写文件时，默认命名为 `<代码解释目录>/{YYYYMMDD-HH}-{TOPIC}-{COMMIT-ID}.md`，目录按需创建；用户明确指定路径或者文件名时，遵循其要求。

`{YYYYMMDD-HH}` 取文档创建时的 Asia/Shanghai 时间，文件名精确到小时，`HH` 使用 24 小时制；正文时间仍精确到分钟。`{TOPIC}` 使用简短、可辨识的主题名称，单词间以 `-` 分隔。

`{COMMIT-ID}` 使用所解释代码对应提交的前 8 位哈希；解释范围包含未提交或者未跟踪内容，或者仓库尚无提交时，使用 `WORKTREE`。文档中的完整提交哈希、基准提交和相关未提交文件等来源信息依照第十条记录；新建文件重名时依照第十一条处理。

### 第三十三条【侦察文档】

侦察文档用于记录代码研究结果，应当说明研究问题、已确认事实、文件路径和行号依据，以及尚未确认的问题。

侦察文档命名为 `<侦察文档目录>/YYYYMMDD-HHmm-RESEARCH-<revision>-<topic>.md`；来源信息依照第九条至第十一条记录。

### 第三十四条【Review】

用户要求 Review 时，默认在回复中给出结果；只有明确要求形成文档时才写入文件。Review 请求本身不授权修改被审查内容；用户同时要求修复时再实施。

Review 应当优先关注缺陷、行为回归、规则冲突和缺失的验证，按严重性排序。每条发现应当说明触发条件、影响和代码或者文档依据，并给出必要的修正建议；不得把个人风格偏好当作缺陷。没有发现问题时，应当明确说明，并指出相关验证空白或者剩余不确定性。

Review 文档命名为 `<Review 文档目录>/YYYYMMDD-HHmm-REVIEW-<model>-<revision>-<topic>.md`。

用户要求复核已有 Review 时，应当逐条核实并说明依据；需要输出文档时，在原文件的 `.md` 前追加 `-review-verification-<model>`，保留原目录，正文记录本次复核的实际版本。此处 `<model>` 为复核模型。

### 第三十五条【逆向功能规格说明书】

用户要求生成 RFS 时，默认覆盖整个仓库；指定模块时只覆盖指定范围。RFS 基于代码恢复现有行为，区分代码事实和未知项，不得把改进建议写成现有功能。

内容应当覆盖用户可见行为、输入输出、数据边界、状态变化、异常处理、权限配置和外部交互，并提供对应代码依据。文档命名为 `<逆向功能规格说明书目录>/YYYYMMDD-HHmm-RFS-<revision>-<topic>.md`。

完成后至少复核一次，以不了解原代码的团队能够据此实现行为一致的替代品为目标；对无法从代码确认的外部依赖和运行时行为，应当明确记录待验证项。

### 第三十六条【交接文档】

用户明确要求，或者未完成的长任务需要暂停、资源限制影响继续执行时，应当更新交接文档。不得猜测无法获取的剩余额度。

交接内容包括项目背景、已完成工作、工作区状态、已知问题、待办和建议的下一步，以及相关文档、代码路径和 commit ID。应当区分已验证结论与假设，使接手者能够继续工作。

## 第九章 任务结束

### 第三十七条【结束报告】

任务结束时，应当简要说明完成内容、关键文件、验证结果和未完成事项；执行了提交或者推送时，报告实际状态。问题解决后结束，不追加无关任务，也不重复索要已经获得的授权。
